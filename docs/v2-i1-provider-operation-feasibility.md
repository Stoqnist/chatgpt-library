# I1 provider-operation and recovery feasibility review

**Reviewed 2026-10-14. Decision record, not a live adapter or release authorization.**
Reference state: experimental V2 PRs [#34](https://github.com/Stoqnist/chatgpt-library/pull/34), [#36](https://github.com/Stoqnist/chatgpt-library/pull/36), [#38](https://github.com/Stoqnist/chatgpt-library/pull/38), [#40](https://github.com/Stoqnist/chatgpt-library/pull/40), and [#42](https://github.com/Stoqnist/chatgpt-library/pull/42). #42 merged into **experimental V2** as `10e00ef`, not `main` or deployed V1.

## Scope and evidence standard

This review covers only I1's three **proposed fictional effects**: Health note (`health_note` or `mental_note`), Purchase lifecycle review note (`purchase_note`), and neutral Calendar follow-up (`calendar_create`). Stock decrement, bank transactions, purchase orders, payments, notifications and clinical decisions are **outside this integration**.

Evidence levels are distinct: **reported read** = prior P4 review describes a limited real read; **tool contract** = currently advertised connector operation, not an observed authorized call; **API documented** = provider's published API behavior; **unknown** = no verified principal/permission, live side-effect semantics, or recovery outcome. **No new personal-provider calls, event creation, file edits, provider probes, model charges or deployment were performed for this review.** Public notes omit private identifiers and personal contents.

### Calendar-specific tool-contract finding

The connected `Google_Calendar.create_event` tool **does not expose a caller-defined event ID or an explicit `sendUpdates` option**. Its documented defaults include `add_google_meet=true` and `timezone_str="America/Los_Angeles"`. A hypothetical user-authorized neutral follow-up must therefore explicitly set `add_google_meet=false`, `attendees=[]`, a correct explicit timezone, and only approved non-sensitive fields; no implicit conference or invitation may be assumed harmless. Notification behavior remains unverified at this connector boundary; the review **does not** authorize a create trial.

For an event-detail recovery read, the connector advertises `read_event(calendar_id, event_id)` but returns a **full event-detail object** (including optional title, description and attendee fields), with **no exposed field mask**. This does not establish a provider-side minimum-field read; authorized adapters must minimize onward disclosure and separately establish whether narrower collection is available. The existing five-minute free/busy observation cannot prove event-detail access. Google documents `calendar.events.readonly` (and, for owned calendars, `calendar.events.owned.readonly`) as event-detail read scope candidates, and `calendar.events` or `calendar.events.owned` as creation-scope candidates; `calendar.calendarlist.readonly` is for subscription listing. **These are documented candidates, not known granted scopes.** See [Calendar scope reference](https://developers.google.com/workspace/calendar/api/auth).

Google's underlying [events.insert](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert) API permits a client-specified event ID (subject to syntax/collision limits), but this is **not a capability of the currently advertised create tool**. Even the underlying API warns that globally distributed collision detection is not guaranteed: user IDs are a recovery aid, not an exactly-once guarantee. [events.get](https://developers.google.com/workspace/calendar/api/v3/reference/events/get) accepts event-read scopes distinct from free/busy. The connector's broad text search is not a reliable identity oracle when every fictional follow-up uses the neutral title `Personal follow-up`. Until an exact event-identity and recovery strategy is supported **and independently tested on an approved disposable calendar**, any creation timeout with no stable returned ID must remain **unknown**, with **no automatic retry or deletion**.

### Library-specific tool-contract finding

Library's personal-file replacement interface advertises a stable `library_file_id` with a required `expected_current_version` for overwrite by identity. This supports a *potential* optimistic precondition, unlike an unrestricted path overwrite, but **no approved disposable Library conflict/restart/timeout trial has verified its real guarantees**. A version number or current file contents alone may not attribute an ambiguous previous mutation to the intended operation. Before Health or Purchase record editing, require an owner-approved full-file preview, exact identity/version precondition, durable operation fingerprint and attempt evidence, an independently authorized bounded readback, and observed handling of stale versions, uncertain responses and intervening writers. Do **not** create alternate canonical records or assume a safe record write from successful Library search/read.

## Required boundaries for any real I1 recovery adapter

1. **Trusted requester and read authority before lookup.** Bind authenticated principal and domain owner to exact provider/resource/operation; check independent minimum-field **recovery-read** permission before disclosing whether the operation exists. Synthetic `requester_owner` and self-issued mock grants in #40/#42 are not authentication. Keep outward unauthorized/missing-ID denial uniform.
2. **Immutable durable intent + attempt mapping.** Persist a private, minimum-detail `request_id`, `operation_id`, provider destination identity, intent fingerprint, plan generation, original approval provenance and pre-call attempt marker; never put these, private account IDs or raw probe evidence in Git. The mock's in-memory marker has no process-restart guarantee.
3. **Evidence-based readback only.** Confirm the exact intended effect and authorized owner/resource. Different provider errors, missing markers, stale reads, wrong resource, inaccessible read grants, or inconclusive duplicates yield **unknown**, not `verified` or `not applied`. Preserve prior attempted/verified/unknown states and read trace; no blind retry on timeout.
4. **No inferred write authority.** An independent read grant never restores a revoked approval; a prior write approval never grants inspection. A changed/urgent turn blocks new execution, not inspection of a previously attempted uncertain operation. Conditional revisions, concurrency, idempotency and partial failure must be proven separately for each adapter.
5. **No automatic compensation.** A read-only inspection never edits, deletes, invites, orders, refunds or rolls back anything. Compensating effects require separate owner-specific authorization and verified outcome.

## Feasibility decision and next bounded action

- **Feasible now:** additional **offline contract/negative tests** and owner-specific read-only design using prior observations and advertised tools. I1's mock revocation, separate read gate, uniform unauthorized denial and history tracking remain useful *mock evidence*.
- **Not evidenced yet:** a production-safe Calendar create/recovery route; durable Library write attribution; authenticated principal and exact effective grants for recovery reads; provider-side concurrency, post-timeout recovery or independently authorized user consent.
- **Smallest next verification:** under separate authorization, first validate on an **approved disposable target** the exact readback operation, principal/resource binding and minimum returned fields. For Calendar, resolve the stable-ID problem or explicitly choose a manual `unknown` fallback **before** any separately approved event-create trial. For Library, independently check version-conflict and readback semantics on a disposable file, not canonical Health/Purchase records. No general permissions/approval framework or additional mock retry layer.

The formal private OAuth/grant attestation remains **deferred/unverified**, not a prerequisite for this offline review. It cannot be silently replaced with tool availability or successful free/busy reads. Real side effects, P4 permission acceptance, P5 real-model spending, P6 release and V1 deployment remain **blocked**. See also [P4 connector feasibility review](https://github.com/Stoqnist/chatgpt-library/blob/design/v2-orchestration-contract/docs/v2-p4-connector-feasibility.md) in the experimental V2 branch; it has not established this missing provider recovery evidence.
