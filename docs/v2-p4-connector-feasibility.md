# P4 Connector Feasibility and Least-Privilege Review

**Status:** 2026-10-14, experimental audit, not release clearance. This file contains **no private account identifiers**. Repository `main` remains V1; P3 test doubles are not a production API.

## Read-only discovery evidence

The connected capabilities were inspected without changing any record. The registered food spreadsheet was located using the deployed Library architecture; metadata confirmed a native Sheet with a `Stock` tab. Google Drive returned the file MIME type and modification metadata. Calendar list access returned six calendar entries with reader/owner roles and a primary calendar. Library search found current Health, Finance, and Purchase canonical record names with editor role. No sensitive record content, stock quantities, calendar event details, or private locator is included here.

These observations establish **only metadata discovery**, and may become stale. They do **not** verify OAuth scope grants, principal identity, effective write rights, target ownership for execution, delivery of notifications, version-based compare-and-swap, or idempotency after timeout. Private bindings and operational facts remain outside Git.

## Least-privilege execution contract

1. Resolve canonical provider and owner from the current deployed architecture; obtain private resource bindings at runtime. Do not infer mappings from mock destinations or Git.
2. Start read-only; read only the minimum authorized fields. Health detail must not reach Finance/Purchase/Calendar. Return unknown for stale or inaccessible sources; do not substitute old chat or screenshots.
3. Treat a successful metadata probe as metadata only. For a synthetic **read** probe, compare the stated ACL role against the minimum read role (`viewer` for Library, `reader` for Sheets/Calendar): editor/writer/owner is flagged `excess_read_privilege` and blocked until a separately reviewed exception or narrower connection is established. The independent synthetic OAuth posture check now rejects a minimal ACL paired with broad/unknown scopes, or an elevated ACL paired with minimal scopes. Neither synthetic classification is a real effective-grants, principal, ACL-inheritance or OAuth scope audit; no exception is granted here. The offline P4 classifier has **no execution path** and always returns `execution_allowed=false`, even when all synthetic capabilities are true.
4. For a **separately authorized** future disposable write: confirm dedicated test resource, principal, required provider scopes, owner, exact operation preview and explicit user approval; verify current version and that no other writer has changed it.
5. Execute only through an independently gated adapter. Capture attempt/operation ID, provider response, provider state after readback, partial outcomes and unknown state. Inspect unknown outcomes before retry; never assume exactly-once or transactional writes.
6. No production or private-record writing, deletions, purchasing, notification delivery, or calendar mutations occur in this PR or CI.

## Remaining gaps and repair plan

- **Library:** Tool-level version preconditions and partial failure semantics must be exercised against an **approved disposable Library target** without overwriting canonical identities.
- **Sheets:** Google Sheets lacks an established database-level compare-and-set guarantee in this architecture; serialize owner writes, reread current rows, and fail on conflict. Recover through authoritative readback rather than blind retry.
- **Calendar:** Calendar roles can differ between calendars; confirm the specific target ACL. Create a one-off neutral-titled event only in a separately approved disposable test calendar, verify with read, and delete only with separate explicit authorization. Unknown create results require bounded search and inspection; do not promise an exactly-once event.
- **Finance/Purchase:** External account and order APIs are not inspected or authorized by this metadata check; real purchase/payment actions are out of scope.
- **Identity/scope:** Effective OAuth grants, tenant/account identity and private resource bindings were not obtained. A synthetic minimum-role regression now rejects overprivileged read ACLs, but does **not** prove actual granted scopes or effective permissions; these still require private, provider-specific verification. Discovery is not authorization.
- **Privacy/operations:** Keep private probe logs and identifiers out of CI, repo, and artifacts. For live tests, keep redacted event IDs, exact provider error type, and manual repair status privately.
- **Rollback:** Multi-provider operations are not atomic; no automatic global rollback. For each verified partial write, stop new dependent actions, report verified changes, seek owner/user approval for compensating action, then verify compensation. Do not delete an uncertain write blindly.

This follow-up exercised **bounded provider reads** on the user's registered destinations. All operations were read-only and did not invoke the offline classifier as an authorization source.

| Destination | Directly observed | Still **not** established |
| --- | --- | --- |

| Google Calendar | Connected Drive and Calendar profiles matched; calendar-list ACL roles were discoverable; a five-minute `primary` free/busy read succeeded without titles or attendee details | OAuth grant set, full event-read ability, notifications, calendar owner authorization for actual follow-up events, or effect of retries |
| External Finance/Purchase providers | Relevant canonical Library records located and minimally readable | Any authenticated bank, payment, merchant, ordering or refund API access; no such trial was conducted |

**Interpretation:** provider metadata + a successful narrow read prove those individual read operations were accessible at the time of the probe, not that their connectors had minimal OAuth scopes or that future reads/writes will behave identically. Drive permission listings may include owner/reader entries unrelated to the active effective principal. Library editor roles and Calendar owner roles alone are not evidence of effective OAuth powers. `freeBusyReader` and event-detail readers have different capabilities; a free/busy success does not establish event reading.

**Open P4 permission gate:** establish privately, per provider/operation, the effective principal, exact granted OAuth scopes or documented inability to inspect them, resource-level ACL/inheritance, minimum fields, and relevant provider-side audit. If any component is unknown or broader than necessary, retain `blocked` and document a narrower connection or reviewed exception. Keep read-only access and explicit `execution_allowed=false`; no trial here authorizes new permissions, production writes, paid model calls, deployment or I1.

## 2026-10-14 provider identity and minimum-read grant audit

**Scope:** read-only access on the existing registered destinations. Provider account identities, resource IDs, permission grantee details, raw API responses and any credential material are deliberately excluded from this public repository. This section records only minimized outcomes; it is **not a private token-grant attestation**.

| Provider / exact operation | Observed principal and resource access | Provider-documented narrow OAuth scope candidate | P4 grant finding |
| --- | --- | --- | --- |
| ChatGPT Library: search for canonical Health/Finance/Purchase files, then bounded one-line reads | Registered files were found; bounded reads succeeded; `editor` role visible. No independent authenticated Library principal or equivalent delegated token grant was exposed. | Library reader/viewer access is the least-rights **design target**, but a viewer-only connection was not separately tested; Google OAuth scopes do not apply to Library | **Unverified** principal and effective grant; observed editor is broader than read needs |
| Google Drive: `files.get` metadata and available permission information for the registered food spreadsheet | Drive profile returned an account identity; it matched one `owner` permission entry for the registered file. The file was accessible, but other entries do not describe the connector's OAuth rights. | `drive.metadata.readonly` is an accepted metadata-read OAuth scope; access to full permissions detail also depends on the principal's ability to share/view ACLs | **Unverified** actual token scopes and inherited privileges; owner ACL is account/resource authority, **not** proof the connector token has write scope |
| Google Sheets: `spreadsheets.get` native metadata and `spreadsheets.values.get` for `Stock!A1:K1` only | The registered tab was present and all eleven expected header labels matched; no current-stock rows were read | `spreadsheets.readonly` can support both operations; it is read-only but broadly covers Sheets files, not just a single tab | **Unverified** token grant and access outside the selected header; no read scope can be assumed tab-restricted |
| Google Calendar: `calendarList.list` | Calendar profile returned the same account identity as Drive; calendar-list call succeeded and the primary entry reported `owner` | `calendar.calendarlist.readonly` supports listing subscriptions; a `freeBusyReader` calendar role may appear in the list | **Unverified** granted scopes; observed calendar owner status must not imply an event-write token |
| Google Calendar: `freeBusy.query` limited to a five-minute interval on `primary` | Free/busy result succeeded with no per-calendar error; no event title, attendee, or description was requested | `calendar.freebusy` or `calendar.events.freebusy` is an accepted narrow scope, with `freeBusyReader` as the minimal calendar-level role | **Unverified** which token scope was actually granted; this probe does not establish event-detail access |

Official API references: [Drive files.get](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/get), [Sheets spreadsheets.get](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets/get), [Sheets values.get](https://developers.google.com/workspace/sheets/api/reference/rest/v4/spreadsheets.values/get), [Calendar calendarList.list](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList/list), [Calendar freebusy.query](https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query). Listed scopes are **accepted alternatives/design targets, not observed grants**. Access roles and OAuth scopes are separate independent dimensions. Google Sheets API scopes cannot be restricted to one worksheet/tab; `drive.file` can narrow resource selection but also permits edits to selected files and is **not** an equivalent read-only replacement.

**Gate result:** The individual reads and Google profile-to-owner-ACL association are observed; *effective OAuth token scope lists are not returned by the connected tools*, nor is the Library's complete authenticated-principal/grants model. Do not mark `scope_verified=true` or `oauth_scope_posture=minimal_read` from these observations. Resolve grants by a private provider-authorized consent/scope audit, or record them as unknown and keep P4 blocked. Do not alter owner ACLs merely to make read-only test metadata appear minimal; first constrain and verify connector scopes, and separately document unavoidable resource-owner rights. No tokens, personal record contents or private probe logs are published.

## P4 acceptance status

**Offline preflight implementation:** implemented and CI-checkable; verifies structural owner/provider gates and rejected permission/stale/timeout/scope cases. **Live bounded read probes:** performed for registered Library, Sheets and Calendar operations only; observed access does not prove scope minimization or full feature support. **Live mutation/execution integration:** not run and requires separate approval. **Production readiness:** blocked until private provider-grants assessment, authorized disposable trial, failure-recovery review and explicit release decision. Passing synthetic tests or read probes must not lift P6 release gates.
