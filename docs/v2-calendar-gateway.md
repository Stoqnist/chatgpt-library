# V2 Calendar Gateway — offline implementation

**Status:** Prototype on the experimental V2 branch, not a deployed VPS server. No HTTP listener, real OAuth connection, provisioned vault key, actual VPS configuration, live Google read or write, or user consent for provider side effects is part of this PR. V1 and canonical agent record ownership are unchanged.

## Narrow ownership and authorization boundary

The core verifies a short-lived, signed caller assertion (configured signing key, audience, calendar ID, **exact operation ID**, role and expiry) **before** accessing an operation record. The offline core does not authenticate a live issuer or prevent replay. Only the role calendar_executor may prepare an event and register a separately approved attempt; only calendar_recovery may inspect an attempted operation. These are trusted-service roles, not self-identified AI-agent strings. **No real assertion issuer, external authentication service, TLS boundary or replay defense is implemented in this prototype.** Signing keys must remain outside agents, source control and routine logs. User approval is a separate exact-intent verifier; a mock callback cannot stand in for real user consent. The gateway does not implement event creation or a general-purpose permissions framework.

Google OAuth scopes govern what the **application** may access, not what an individual AI agent may access. For least privilege, configure one separately approved Calendar resource and a minimum accepted Calendar OAuth grant; consider an app-created secondary calendar and the calendar.app.created scope only if its creation and isolation are separately approved. That scope does not apply automatically to existing personal calendars.

## Offline session-bound consent issuance and revocation (experimental)

The fictional `OfflineConsentIssuer` accepts two external **Ed25519 public-key-verified input assertion** sources—session and UI confirmation—and holds an **Ed25519 private signing key** for the final exact-intent approval. The Gateway's `OfflineApprovalVerifier` receives **only an explicitly configured map of Ed25519 public verification keys** indexed by signed `kid`; it cannot sign an approval. HMAC approval proofs are rejected. A challenge binds the configured calendar, operation, event ID and canonical plan digest to a specific subject/session and a short expiry. The issuer returns a **safe display representation** (neutral summary, event dates, calendar, visibility, reminders, action and operation) for an external trusted confirmation UI. It cannot display a user interface, authenticate a human, collect consent or mint a session/UI assertion. Positive test fixtures are fictional keys and manually generated signed assertions; **they are not actual user approvals**.

On a valid affirmative UI confirmation, the issuer signs the existing PR #58 approval format and stores an opaque receipt in the *same fictional SQLite file* as `IntentLedger`. When instantiated with `require_approval_registry=True`, the ledger requires an active matching, unexpired receipt and transitions it from `issued` to `consumed` **in the same SQLite transaction** as the conditional attempt-state update. Revocation requires the bound session and affects only still-`issued` receipts. A revoked or expired receipt fails before the synthetic attempt even if revocation/expiry happens **after** preliminary signature verification. A consumed receipt cannot be revoked to undo an attempted external effect; a real cancellation is a separate, explicitly authorized workflow. Challenge decisions are one-shot, including decline. Reopening the same synthetic database retains pending/issued/revoked/consumed states.

**Limits and deployment gates:** This is a testable *trust contract*, not a deployed identity provider. Production would require real IdP signature validation and session revocation, a trusted UI with independently authenticated intent display and explicit consent evidence, secured issuer keys/rotation and per-principal authorization, provider grants, audited issuance/revocation, transactional storage ownership and crash/concurrent-process tests. **Cryptographic approval-key separation is now implemented offline:** issuer private Ed25519 signing and Gateway public-only Ed25519 verification are distinct; a signed `kid`, approval receipt's recorded signing key, and registry status must match. This only proves cryptographic separation of the **approval proof**, not a real independently administered key-distribution service. The fictional session and UI inputs now use separate public-key-only Ed25519 verifiers, but their signed test fixtures still do not prove real authenticated consent or trustworthy display. The ledger now defaults to **`require_approval_registry=True`** (fail closed). Only legacy synthetic test fixtures may explicitly opt out with `require_approval_registry=False`; this compatibility mode must never be used for real execution. Revocation across multiple databases or processes, lost issuance responses, backup/restore, user withdrawal *after* an attempt, Google event creation and provider timeout recovery remain unproven. No new Calendar write endpoint, OAuth grant, account binding or deployment is authorized.

## Offline external identity and consent-display trust contract

The experimental consent issuer now consumes **verification-only** Ed25519 assertions from two separate externally governed public-key allowlists: a purported identity-provider session issuer and an independent consent UI. These are pinned locally by issuer, audience, purpose/type and key ID. Assertions are short-lived, include issuance time, bind a subject and session ID, and cannot be self-signed by the Calendar issuer or accepted via dynamic URL/key discovery. The Calendar consent issuer requires explicit callbacks returning fresh **active-session** and **subject-to-calendar access** decisions; absence of either fails closed. Access and session state are checked again immediately before the one-shot consent decision is recorded.

The consent challenge now stores the SHA-256 digest of the **exact canonical preview** in addition to the complete planned-event digest. The independent UI assertion must bind subject, session, challenge ID, exact plan digest, **exact preview digest**, and an explicit affirmative or declined decision. The preview includes Calendar/action/event identifiers, interval, privacy, no-attendee/no-conference configuration, reminders, and insert flags. The original Ed25519 approval proof and receipt/signing-key CAS remain unchanged; this is an input trust-contract upgrade, not a second approval planner.

**Do not conflate contract checks with deployment proof:** All test session and consent UI signatures are minted by fictional test fixtures, not an actual IdP or browser. A trusted UI must genuinely display the attested content and protect user interaction against spoofing/CSRF/clickjacking; a valid preview hash merely verifies what an external UI *claims* it displayed. A real IdP adapter must authenticate session provenance, establish token type and revocation freshness, distinguish access from identity tokens, validate scoped principal grants, and manage trust-key rotation securely. Injected active-session/access callbacks do not provide atomic revocation across SQLite and an external identity provider; a revoked session or calendar grant **after** issuing an approval receipt does not automatically revoke the existing receipt unless a separate trusted revocation event updates its registry. Production requires such event propagation and a revalidation policy before provider effects, with conservative `unknown` handling. No real tokens, browser session, Calendar writes, OAuth permissions or deployment are authorized.

## Selected external providers and single-user hosting model — not provisioned

**Selection: Google OpenID Connect for identity; Google Calendar API for permissions; one private same-origin VPS backend-for-frontend (BFF) for consent.** Propose a persistent Cloudflare Tunnel to a fixed HTTPS hostname on a user-controlled DNS zone; the VPS service binds to localhost/private networking with no unauthenticated fallback. A tunnel is transport, not login. Neither the user's VPS/domain/tunnel nor any Google Cloud OAuth client has been inspected, provisioned or deployed. One BFF simplifies browser boundaries but does not prove organizational independence of UI attestation and issuer signing keys; separate protected signing-key access remains required.

**OIDC login:** After separately authorized Google Cloud setup, use a confidential web client, exact HTTPS callback, Authorization Code + PKCE S256, state and nonce, and a trusted Google OIDC library verifying JWKS signature, issuer, client audience, azp when required, sub, expiry and issuance. Use Google's stable sub, not email, as identity. The BFF generates its own unpredictable server-side session ID and persists session expiry/revocation. Google's real ID token must be verified with Google's published algorithm/JWKS, not fed directly to the internal fictional Ed25519 verifier; a separate authenticated adapter would issue the internal session assertion. Google global account logout is NOT verified to deliver a timely back-channel logout event to Agency. Only the local BFF can currently promise to invalidate its own session on local logout.

**Trusted same-origin consent:** Serve the exact server-generated Calendar preview on the BFF HTTPS origin with secure HttpOnly SameSite cookies, strict state/nonce, CSRF/Origin protection, CSP and frame restrictions. Require an actual explicit Approve or Decline POST, bound to the authenticated BFF session and one-use short-lived challenge. A protected UI attester signs the canonical preview hash, plan digest, subject/session/challenge and decision only after validated user interaction. Never expose private keys or OAuth tokens to browsers, ChatGPT agents or connector messages. This remains a specification, not a working UI.

**Separate Calendar OAuth authority:** Obtain a separately approved Calendar OAuth client and grant bound to the same verified Google account subject. For the first, narrow owned-calendar target, propose the scopes https://www.googleapis.com/auth/calendar.events.owned and https://www.googleapis.com/auth/calendar.calendarlist.readonly. Verify the actual OAuth client, grant scopes, token owner and validity plus exact calendar ID and effective owner role with an authenticated live CalendarList query. This policy intentionally does NOT authorize shared writer calendars; broader scope/role support needs new review. Connected ChatGPT Calendar metadata is from a *different* connector and does not prove the prospective Agency OAuth client or its write scopes. No private calendar IDs, emails or token contents are stored in public Git.

**Freshness policy, currently offline:** The synthetic evaluator calendar_google_authority.evaluate_google_owned_calendar_preflight requires independently verified Google-ID-token/BFF-session evidence, fresh active local session, explicit consent, matching account, a separately bound Calendar OAuth client, active granted owned-event-write and calendar-list-read scopes, a fresh exact owner role and unexpired grant. Proposed test maxima are 30 seconds for session, grant and role observations, and 120 seconds for explicit consent. These are conservative design parameters, NOT verified provider freshness SLAs. A passing synthetic result is explicitly NOT authority for a live provider write; validation of actual Google JWTs, OAuth scope grants and principal binding is not implemented in this module.

**Logout, permission loss and fail-closed external actions:** A BFF logout must terminate its own session and propagate a trusted session tombstone to the existing consent ledger. A separately verified Calendar token/grant failure or resource permission-loss signal must tombstone the bound user/calendar and invalidate pending and issued-but-unconsumed approvals. Production would require current authenticated session and Calendar authority evidence immediately before each provider write, denying missing/stale/unknown evidence. Cross-provider revocation is not atomic: missed, late or revoked-after-check external state cannot be guaranteed instantly synchronized with SQLite. Already attempted unknown outcomes cannot be undone or blindly retried. No live auth, Calendar write, domain publication or VPS deployment is approved by this selection.

**Official documentation:** [Google OIDC](https://developers.google.com/identity/openid-connect/reference), [Google ID token verification](https://developers.google.com/identity/sign-in/web/backend-auth), [Calendar OAuth scopes](https://developers.google.com/workspace/calendar/api/auth), [CalendarList roles](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList), [Cloudflare origin protection](https://developers.cloudflare.com/fundamentals/security/protect-your-origin-server/), [OIDC back-channel logout standard](https://openid.net/specs/openid-connect-backchannel-1_0.html) (not a claim Google sends logout tokens to Agency).

## Proposed real identity-provider and trusted consent UI integration — contract only

**Architecture ownership:** A single user-facing backend-for-frontend (BFF) owns browser sessions, OIDC login and the consent screen. A separate Consent Issuer owns the short-lived challenge/receipt record and Ed25519 approval **private** key. The Calendar Gateway has only the public verifier and reads the same protected attempt/receipt registry; AI agents receive no login cookies, OAuth tokens, signing keys, or direct approval capability. The actual IdP and deployment origin are **not selected or connected**. Require an issuer supporting an adequate logout/revocation profile; do not presume every IdP supports OIDC back-channel logout or `sid`.

**Authentication:** Use a specifically approved OIDC relying party, Authorization Code + PKCE (S256), exact redirect URI, issuer/audience/nonce/state validation, secure server-side session mapping of the IdP's `iss`, `sub`, optional `sid`, expiry and logout state; HTTP-only, Secure, SameSite session cookies. Keep access/refresh/ID tokens server-side and distinguish identity tokens from Google Calendar access grants. A fresh `session_active` verdict must originate from the authenticated BFF/session authority, not a request-body flag or AI-produced assertion. For multiple IdPs, namespace user identity by `(issuer,subject)` before mapping to the internal stable `subject`; do not reuse a display name or email as an identity key.

**Trusted consent UX:** The BFF renders the exact canonical server-generated preview (resource/action, interval, privacy, attendees, notifications/reminders, and consent limitations) over HTTPS, on an approved fixed origin, with accessible explicit **Approve** and **Decline** controls. POST only after a fresh user interaction, with CSRF protection, Origin checks, one-use browser/session-bound challenge nonce, short expiry, Content Security Policy and frame-embedding restrictions. The separate UI-signing authority must attest the same subject/session, plan digest, challenge ID and **display SHA-256** only after verified display plus affirmative interaction. No agent can sign UI proof, and the browser must never contain issuer or UI signing keys. An assertion hash alone does not establish a human saw the preview; production deployment must verify origin, rendering, authentication strength and audit events with real browser tests.

**Calendar permission evidence:** The chosen Calendar connection and its approved OAuth scopes are a **different authority from OIDC login**. Before granting a pending consent or attempting an external effect, a protected server-side Calendar adapter must verify the bound account, selected exact calendar ID, OAuth grant health and effective event-write permission for that resource. Google Calendar's documented CalendarList `accessRole` values include writer and owner; a read-only role does not authorize inserting events. Distinguish direct ACL/Calendar access loss from token revocation (`invalid_grant`, 401/403, disconnected integration). Calendar push/ACL watch signals may trigger *invalidation*, but no webhook alone proves current authorization. Exact scopes, quotas, role visibility and read permissions must be independently validated before any live action.

**Revocation path:** An authenticated IdP session logout (or signed OIDC Back-Channel Logout Token when actually supported) maps the validated issuer+subject and optionally `sid` to the registered internal subject/session. A validated permission-loss signal maps the **bound OAuth principal and calendar**, not a user-supplied calendar string. Both call a narrow, non-public `apply_verified_revocation` sink only **after** validating issuer/signature/audience, event identity, replay, freshness and authorized ownership. It records an idempotent event ID and a persistent **monotonic tombstone** in the *same SQLite database* as approval receipts, revokes all matching unconsumed issued approvals and pending challenges in one `BEGIN IMMEDIATE` transaction, and the final attempt CAS rechecks those tombstones under the same lock. Supported scopes: session (one subject+sid), principal (every session of the subject) and calendar (subject's selected calendar). A repeated event is idempotent; a reused event ID with different meaning is rejected. Revocation does not undo an already-consumed attempt, does not authorize deletion of any real event, and reopening a tombstoned grant requires **new validated authorization, a fresh operation and fresh consent** under a future separately reviewed lifecycle.

**Fundamental distributed-systems limit:** Local SQLite is atomic only with its own recorded revocation events, **not with remote IdP/Google state**. Late, lost or spoofed logout/ACL notifications cannot guarantee instantaneous invalidation. A real executor MUST require a fresh, bounded-age authenticated session/Calendar authority verdict (or trusted short-lived lease with explicit issuer/account/resource/expiry) immediately before any provider write and fail closed when freshness, scope or revocation synchronization is unknown. Even that cannot create a distributed atomic transaction with Google: if authority changes after the final remote check, record an ambiguous outcome, never blind-retry an event, and require exact-ID inspection or manual reconciliation. Do not treat successful webhook receipt, expired cached identity or stale OAuth grant as positive proof.

**Official references:** [OIDC Back-Channel Logout 1.0](https://openid.net/specs/openid-connect-backchannel-1_0.html) (signed logout tokens; `sid` or `sub`; nonce prohibited), [RFC 9700 OAuth Security BCP](https://www.rfc-editor.org/rfc/rfc9700.html) (PKCE, CSRF, exact redirects), [RFC 7009 Token Revocation](https://www.rfc-editor.org/rfc/rfc7009.html), [Google Calendar CalendarList accessRole](https://developers.google.com/workspace/calendar/api/v3/reference/calendarList). These are future adapter design requirements, not assertions of an existing account's IdP or grants.

**Prototype scope:** `OfflineConsentIssuer.apply_verified_revocation` accepts a *normalized prevalidated synthetic event*; it deliberately has **no authentication layer or network endpoint**. It must never be exposed directly to the Internet or ChatGPT tools. Offline tests cover same-DB revocation/attempt interleavings but do not prove actual signed OIDC logout-token validation, HTTP consent security, Google ACL observation, event delivery reliability, cross-host recovery or live user consent.

## Offline approval signing-key rotation and compromise handling

Approval proofs now use Ed25519 over the compact encoded claims body (`alg=EdDSA`, fixed approval type, signed `kid`), rather than shared-secret HMAC. The verifier must be initialized from a trusted public-key allowlist; unknown IDs, altered algorithm/type, swapped signatures, private signing keys passed to a verifier and forged signed claims fail closed. No key-discovery URL, self-advertised public key or JWK auto-import is accepted. Test keys are **fictional** and must never be provisioned to a real issuer.

An offline operator test can register a new signing key ID, distribute its public verification key through **separate trusted configuration**, and retire the old ID. The old public key may remain on the verifier's allowlist only for the short remaining lifetime of previously issued approvals. Retired key IDs cannot issue new approvals. Marking a key **compromised** (test-only simulated administrative action) revokes its unconsumed approval receipts in the same SQLite database; the attempt CAS checks the signed key ID matches the receipt and rejects receipts from compromised keys even if the Ed25519 signature is mathematically valid. A compromise happening after signature verification but before the attempt CAS therefore fails closed. Already-consumed attempts cannot be undone by key quarantine.

**SQLite transaction-ordering pitfall corrected:** Python's `with sqlite3.Connection` context manager does not itself reserve a write lock for an initial `SELECT`. The attempt CAS now executes `BEGIN IMMEDIATE` *before* reading the approval receipt and key status, and the issuer likewise serializes challenge decisions and key-state changes before their read-then-write steps. An offline second-connection regression checks that a competing writer cannot change the key state in that window. These tests do not establish cross-host or external-provider transactional safety.

**Deployment-critical limits:** `set_key_state` is an **offline operator fixture**, not an authenticated administrator endpoint. Real key rotation and emergency compromise response require independently protected key custody, verified public-key distribution, fail-closed update sequencing, audit trails, mandatory maximum validity windows, and revocation across all instances/stores. A compromised private signer can mint signatures, but should not be able to register an approval receipt without access to the separately controlled ledger; this database/control separation is **not proven** here. Do not assume revoking keys restores a compromised consent history or reverses an external Calendar action. Real login/session and trusted UI proof are still fictional HMAC assertions; no production principal, Google grants or provider writes are authorized.

## OAuth refresh design

The OfflineOAuth core builds a one-use Authorization Code + PKCE URL using access_type=offline, checks callback state and granted scopes, stores a refresh token only via an **injected private vault**, and silently requests a short-lived access token when necessary using an **injected Google HTTPS exchange client**. A minimal GoogleHTTPS adapter is implemented with fixed Google token and exact-ID Calendar read endpoints, default TLS verification, redirect refusal and bounded JSON/error responses; no general URL proxy or Calendar write operation exists. An offline implementation now provides EncryptedFileVault with AES-256-GCM authenticated encryption, owner-only directory/file checks, atomic replace and directory fsync. Its key must be provisioned independently through the VPS secret manager or protected root-only key file, **never next to its ciphertext or inside Git**. Concurrent writers, encryption-key rotation, backup/restore and actual VPS provisioning remain unverified. Missing, tampered or insecure vault data fails closed. A revoked or missing refresh token yields a reauthorization-needed outcome rather than attempts to recover automatically.

For production consent setup, **do not leave an external Google app in Testing indefinitely**: refresh tokens for Calendar scopes are generally subject to seven-day expiry in that mode. The VPS needs its own OAuth client; existing ChatGPT Google credentials are neither assumed transferable nor requested.

## Durable, exact readback design

PR #52's `calendar_rest_intent.plan_insert` is the **only** event identity and neutral-payload planner. Given a separately provisioned durable HMAC key, stable request ID, operation ID, calendar, time interval and IANA timezone, it produces the deterministic, Google-compatible ID. The Gateway ledger stores that entire canonical plan in a synthetic SQLite test DB; it generates **no random event ID, additional marker or competing preview**. A same-intent preparation before any attempt is idempotent, while changed intent or attempts after an unknown outcome fail closed. Reopening the test ledger preserves the planned ID. Existing earlier gateway ledger schemas are not migrated by this offline prototype. The attempt state is committed before any hypothetical provider call, then recovery invokes the **same planner's** `verify_exact_readback` comparator on a fresh exact-ID GET: matching status, neutral/private/nonblocking event, guests/reminders/conference restrictions, timestamp instants and IANA timezone. No separate marker-based comparator remains. Wrong owner, bad assertion, unknown ID and non-attempted ID fail before provider read. The fixed read projection comes from `calendar_rest_intent.READ_FIELDS` and preserves the explicit timezone; timestamp-equivalent timezone offsets are accepted only when the event retains the expected IANA zone. Each recovery call reads provider evidence afresh; a prior `verified` ledger marker is historical and does not prove the event is unchanged now. A missing event, read error, changed identity, mismatched time, missing/changed timezone or cancelled event stays unknown; nothing retries, writes or deletes in the recovery path. No Calendar POST is implemented.

The synthetic ledger now uses full-plan conditional updates both when marking an approved attempt and when recording a matching event read. If the operation's stored identity changes or disappears between steps, the transition fails closed (`unknown` for recovery) rather than reporting a verified different intent. The offline race regressions simulate changed/deleted rows; they do **not** prove production process concurrency, SQLite host security, or crash-safe coordination with Google.

Opaque private extended event properties are **not secret storage**. There is no atomic transaction across SQLite and Google. The current ledger is only an offline test fixture; production durability, single-writer behavior and read authority require independent proof.

2. Provision an approved disposable Calendar and existing harmless test event; separately authorize exact event-ID readback with only needed fields.
3. Wire and review the implemented encrypted-vault and HTTPS client **on a privately configured VPS**, with secret-key provisioning, single-writer enforcement, backup/restore, process-level isolation, trusted caller issuer, TLS-only ingress, and safe audit metadata.
